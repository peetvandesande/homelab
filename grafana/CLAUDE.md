# Grafana

CT 104, **192.168.8.54**. UI over TLS on `:3000`, reaching Prometheus over TLS.

## Working on this

`root/` mirrors the container filesystem and is the source of truth.
`scripts/deploy.sh` pushes it; `scripts/verify.sh` checks the UI, the chain and
the trust path to Prometheus.

Deploy **after** `prometheus/` — the datasource pushed here points at `https`,
so doing it first leaves every dashboard broken in between.

## Invariants

1. **TLS is configured with `GF_*` environment variables in a systemd drop-in,
   not by editing `/etc/grafana/grafana.ini`.** That file is ~2000 lines of
   packaged defaults, currently untouched; owning a copy here would mean
   re-merging it on every Grafana upgrade. `GF_SERVER_*` overrides the ini and
   is the documented mechanism.

2. **Grafana verifies Prometheus against the system trust store**, into which
   `ca/scripts/enrol.sh` installed the G2 root. `tlsSkipVerify` stays `false` —
   this is a real check, and setting it true would make the whole migration
   decorative.

3. **The datasource URLs are names**, `prometheus.home` and `loki.home`, since
   the IPv6 rollout. Verification is by name against the DNS SAN the
   certificates already carried, so nothing about invariant 2 changed. Each
   name resolves to an A and a ULA AAAA; RFC 6724 ranks a ULA below IPv4, so
   Grafana still connects over IPv4 in practice — whichever family answers, the
   certificate verifies.

## Verifying trust without credentials

`verify.sh` does not log into Grafana. It asks the equivalent question from
grafana's own container — does a plain `curl` with no `--cacert` reach
Prometheus over TLS? — because that is the same system trust store Grafana
uses. A pass there means the datasource can connect.

4. **Never add or change `uid:` on a provisioned datasource that already
   exists.** Grafana 13 looks the existing one up by that uid, fails with
   "data source not found", and refuses to start — the whole UI goes down,
   and `is-active` still flickers true because `Restart=on-failure` keeps
   relaunching it. `deploy.sh` therefore waits for a 200 from `/api/health`
   before reporting success. To pin a uid, delete the datasource in the UI
   first so provisioning creates it fresh.

## Datasources

Both are provisioned from `root/etc/grafana/provisioning/datasources/` and
read-only in the UI. "Add data source" there does not edit a provisioned one;
it creates an empty duplicate (`loki-1`) beside it. Edit the file and deploy.
`verify.sh` reads Grafana's own database to assert exactly one Loki datasource
exists at the https URL, so a straggler fails the check.

## Dashboards

Provisioned from files too: the provider is
`root/etc/grafana/provisioning/dashboards/homelab.yaml`, the JSON is one file
per dashboard under `root/var/lib/grafana/dashboards/`, and they land in the
"Homelab" folder, read-only in the UI. Edit the JSON and deploy; Grafana
re-reads the directory every 30 s, so a changed dashboard only needs the push
(a *new provider* needs the restart `deploy.sh` does anyway). To prototype in
the UI, "Save as" a copy, export its JSON model, paste it back over the file
and keep the `uid` - the uid is the URL (`/d/<uid>`).

5. **Dashboards reference the Loki datasource through a hidden `${loki}`
   datasource variable, not by uid.** The provisioned datasource has no
   pinned uid (invariant 4 says why one must never be added to a live one),
   so a hard-coded uid would be a guess that breaks on the next reinstall.

6. **Grafana 13 stores dashboards in unified storage** - the `resource`
   table in `grafana.db`, one JSON document per object - and the legacy
   `dashboard` table stays empty. `verify.sh` reads the former. A JSON file
   the provider rejects is logged as a provisioning error and skipped, and
   the file being on disk proves nothing, so `verify.sh` lists each uid it
   expects to find.

Three are provisioned:

| uid | Title | Covers |
|---|---|---|
| `homelab-dns` | DNS stack | themis/delphi/pythia, per-feed blocks, the VPN-domain shunt and its sync |
| `homelab-fleet` | Fleet | all twelve hosts, scrape health, log shipping |
| `homelab-router` | Router and ONT | ONT optics, PLOAM and line errors; WAN, IPv6 prefix, tunnels; Wi-Fi clients, signal and disconnects; the router itself |

`homelab-router` is the first to use `${loki}`: its Wi-Fi disconnect panels
are LogQL over the router's syslog (`router/README.md`, "Logs"), split by the
driver function that ended each connection. Its metrics come from
`router-metrics/`.

Both are generated by hand-written JSON, not exported from the UI, so they are
readable as diffs. Panels carry `description` text explaining what a reading
*means* rather than restating the query — that is the point of keeping them
here. List a new uid in `verify.sh`'s `DASHBOARD_UIDS`.

The `esxi` dashboard was the only other one and went with esther in October
2026.

## Alerting

Grafana does the alerting in this lab — Prometheus has `rule_files` commented
out and no Alertmanager running — so the rules are Grafana unified-alerting
rules, provisioned from
`root/etc/grafana/provisioning/alerting/homelab.yaml` into the same `Homelab`
folder and read-only in the UI. Nineteen rules in two groups, `dns` and
`fleet`, plus the heartbeat in `heartbeat.yaml` (see "Heartbeat" below) and
the `outside` group in `outside.yaml`, which alerts on ruby and jennie probing
each other's public side (`outside/CLAUDE.md`), and the `probes` group in
`probes.yaml`, on the blackbox exporter at home: internet, tunnels, DNS end to
end, and lab certificates. `homeassistant-vm.yaml` covers the Home Assistant
VM's host metrics, collected by lenora over the guest agent
(`homeassistant/CLAUDE.md`, "VM metrics"). `router.yaml` covers the ONT
(PLOAM state, receive power, temperature, loss of downstream sync), the WAN
itself, the IPv6 prefix, whether `router-metrics/` is collecting at all, and
the Wi-Fi station table; tunnels are already in `probes`. Its ONT alerts travel over the line they report on, so
a dead line reaches the phone only afterwards – the heartbeat is what reports
it live.

Forty-three rules in all, and **a new one goes in `verify.sh`'s `RULE_UIDS`** — the
same requirement as `DASHBOARD_UIDS`, and for the same reason: a rule absent
from the list is not asserted, so a provisioning error would drop it silently.
`verify.sh` cross-checks the list against the uids in the provisioned files, so
forgetting now fails the run rather than going unnoticed — four rules
(`textfile-collector-error`, `alerting-evaluation-failing`,
`recursor-servfail-high`, `rpz-feed-failing`) and seven others had gone
unasserted that way until October 2026. It also matches uids exactly; the older
substring match passed `disk-low` on `ha-vm-disk-low` alone.

7. **Alert rules carry the datasource uid, substituted at deploy time.** A rule
   needs `datasourceUid`, and the provisioned datasources have no pinned uid —
   invariant 4 says why one must never be added to a live one. So the files
   carry `@@PROM_DS_UID@@` and `@@LOKI_DS_UID@@`, and `scripts/deploy.sh` reads
   the uids Grafana actually generated out of `grafana.db` and substitutes both,
   the same way `homelab/dns` substitutes secrets at push time. Nothing is
   hardcoded and a rebuild needs no edit.

   A rule naming a uid that no longer exists does not error — it simply never
   evaluates, silently. `verify.sh` therefore asserts, per datasource and by
   name, that the uid Grafana holds appears in the pushed rules, and separately
   that no `@@..._DS_UID@@` placeholder survived. It checks each by name rather
   than taking the first uid it finds, which was correct only while Prometheus
   was the sole datasource in the rules.

8. **Queries threshold a gauge rather than filtering with `== 0`.** `up{job="dns"}`
   with a `lt 1` threshold keeps a series present when things are healthy, so
   `NoData` means something is genuinely missing and can be alerted on. The one
   exception is `systemd-unit-failed`, which *does* filter — the unfiltered
   series set is ~1600 per evaluation across the fleet, which is too many alert
   instances to carry for a metric that is almost always zero. Its
   `noDataState` is `OK` to match, and that asymmetry is deliberate.

9. **`systemd-unit-failed` has no exclusions, and that is only true because
   `fleet/` keeps it true.** It alerts on any failed unit on any host. The one
   thing that used to be failed everywhere, `openipmi.service`, is masked
   fleet-wide instead of filtered here. If this rule starts firing on something
   structural, mask it in `fleet/masked-units` rather than adding a `name!=`
   to this query — an exclusion here hides the next real failure too.

10. **The `pve` job is excluded from the target-down rules.** Its exporter on
   127.0.0.1:9221 has never run, and one permanently firing alert teaches you to
   ignore all of them. Fix the exporter or delete the job; do not "fix" it by
   widening the rule.

11. **Two rules query Loki rather than a metric, because the router cannot
    publish one.** It has no node-exporter and so no textfile collector, so a
    fault or a script that lives only on the router has nothing to export to
    and its log line is the only evidence. `wan-watchdog-acting` is the second
    (`wan-watchdog/CLAUDE.md`); the first is this one.

    **`wifi-sta-table-stale` queries Loki because the fault it watches has no
    metric at all.** The mt7990 driver leaks station entries on
    an MLO teardown: `hostapd` keeps listing a client the driver cannot find, so
    the link is half-registered and may carry no traffic while still looking
    associated. Nothing counts that — the only evidence is the driver's `sta not
    found` line, so the rule counts log lines instead of thresholding a gauge,
    which is the documented exception to invariant 8.

    The threshold is 5 per 10 minutes, `for: 15m`. `router-metrics` polls
    `get_clients` once a minute and each stale entry fails once per poll, so one
    leaked entry is ~10 lines per 10 minutes and a healthy radio is **0** —
    tolerating transients without needing a second leak to fire. Do not raise
    it to silence a leak: one entry is already a client that cannot use that
    band. `execErrState` is `OK` so a Loki outage alerts as a Loki problem via
    its own rules rather than as a Wi-Fi one.

    This was written after 21 October 2026, when a leak at 12:20 went unnoticed
    for 9.5 hours and cost an evening of unusable Wi-Fi; the lab had no signal
    for it at all. `wifi reload` on the router clears it without taking the WAN
    and the ONT down, which a reboot does.

### Delivery: Home Assistant, then the phone

`root/etc/grafana/provisioning/alerting/notifications.yaml` provisions one
contact point, `home-assistant`, and the notification policy. The contact
point is a webhook to `https://192.168.8.90/api/webhook/<id>`; a Home Assistant
automation (`homeassistant/automations/grafana-alerts.yaml`) turns it into a
push to the companion app on `peets_iphone`. Critical alerts arrive as iOS
critical notifications, which sound through Do Not Disturb; warnings as
ordinary ones; resolved-only notifications silently.

The policy groups by folder and alert name, sends after 30 s (criticals 10 s)
and repeats every 12 h (criticals 4 h). Provisioning it replaces the policy
tree set in the UI.

12. **The webhook id is a secret, substituted at deploy time.** It is the only
    credential an HA webhook has, so the file carries `@@HA_WEBHOOK_ID@@` and
    `deploy.sh` fills it from `secrets.env` (git-ignored, mode 600:
    `HA_WEBHOOK_ID=...`, plus `HEALTHCHECKS_PING_URL` below), sending the
    substituted copy over stdin and leaving it `0640 root:grafana`. The same id goes into the HA automation, which is
    pasted into HA's UI by hand; the automation also sets `local_only`.
    `deploy.sh` refuses to run without `secrets.env`.

13. **This path cannot report a home outage.** HA reaches the phone through the
    companion app's push relay, over the home internet connection, and Grafana,
    Prometheus and HA all run at home. An outage of the line, lenora or
    Grafana itself is silent here by construction; detecting it needs
    something outside the house - the heartbeat below.

To test the HA side without waiting for a real alert, post a minimal payload
from grafana's container (it is on the LAN, which `local_only` requires):

```sh
. grafana/secrets.env
ssh root@grafana "curl -sS -X POST -H 'Content-Type: application/json' \
  https://192.168.8.90/api/webhook/$HA_WEBHOOK_ID -d '{\"commonLabels\":{\"alertname\":\"Test\"},
  \"alerts\":[{\"status\":\"firing\",\"labels\":{\"alertname\":\"Test\",\"severity\":\"warning\"},
  \"annotations\":{\"summary\":\"Test from Grafana\"}}]}'"
```

Change `warning` to `critical` to check the critical sound. Grafana's own
"Test" button on the contact point works too, but needs a login.

### Heartbeat: Healthchecks.io

`heartbeat.yaml` holds one rule, `heartbeat`, that fires whenever
`sum(up{job="node"}) > 0`, i.e. always while home is healthy. Its label
`heartbeat=true` routes it, ahead of every other route, to the `healthchecks`
contact point: a webhook to the check's ping URL, re-sent every 5 minutes. The
check on Healthchecks.io (period 5 min, grace 10 min) alerts from outside when
the pings stop - the line, lenora, Prometheus, rule evaluation or Grafana's
notifier, whichever broke. Healthchecks.io's own notifications are configured
there, not here.

14. **Everything other than a healthy answer must stop the pings.** So the
    query asks Prometheus rather than using `vector(1)`, `noDataState` and
    `execErrState` are `OK`, and the contact point has `disableResolveMessage:
    true` - a resolve is a POST as well, and Healthchecks.io would take it as
    a ping. The ping URL is the check's only credential (anyone holding it can
    fake the heartbeat), so it is substituted from `secrets.env` like the
    webhook id.
